## 1. 总体架构

系统采用浏览器/服务器（B/S）结构，按四层组织：

| 层次 | 内容 | 职责 |
| --- | --- | --- |
| 表现层 | 响应式 Web 前端，按角色提供页面 | 展示与输入；电脑和手机均可用（REQ-026）。前端隐藏按钮不作为权限依据 |
| 接口层 | HTTP API、身份认证、输入校验 | 识别游客或登录用户，统一校验参数，把请求转给业务模块 |
| 业务层 | M1～M12 业务模块，外加定时调度 | 执行状态转换、名额计算、权限判断和时间规则 |
| 数据层 | 数据访问、事务管理、关系数据库 | 外键和唯一约束兜底，保证关联更新全部成功或全部不生效（REQ-023、REQ-025） |

实验基本要求 6 项与模块的对应关系：

1. 四类用户的权限 → M1
2. 活动、场次、票种或报名类别的创建、审核、发布、修改和取消 → M2、M3
3. 活动查询、报名、取消报名、候补和自动递补 → M4、M5
4. 多人争抢最后名额、重复报名、截止后报名 → M5（借助 S2 的事务与唯一约束）
5. 签到或验票；重复签到、缺席、活动取消 → M7（活动取消由 M2 发起，M5、M6 同步处理）
6. 名单导出、容量统计、关键操作记录 → M11、M12

## 3. 模块之间的交互

| 调用方 | 被调用方 | 交互内容 |
| --- | --- | --- |
| 所有模块 | M1 | 每次请求先确认身份，再按角色和对象范围鉴权 |
| 所有写操作模块 | M12 | 业务成功或明确失败后写入一条操作日志；重复但未生效的请求不记成新的成功 |
| M5 | M6 | 报名成功时生成正式票；进入候补时生成候补凭证；退票或递补时让旧凭证失效或换发正式票 |
| M5 | M8 | 成功进入候补后发送入队提醒（同一事件只发一次） |
| M3 | M2 | 审核通过后把活动状态改为已发布，或让修改申请生效 |
| M3 | M5 | 增加名额的修改申请通过后，触发同类别候补递补 |
| M2 | M5、M6 | 取消活动、场次或类别时，批量取消范围内的报名并让对应票券失效；同时清空候补队列，删除候补记录和候补凭证，不触发递补 |
| M7 | M6、M5 | 检票时核验正式票，并把报名记录改为已签到 |
| S1 | M5、M7、M2 | 按时间触发候补失效、缺席标记、活动结束 |
| M9 | M7、M2 | 依据真实签到记录判定“已出席”标识，依据活动管理关系判定“活动官方”标识 |
| M10 | M6、M8 | 个人中心读取本人票券和消息 |
| M11 | M5、M7 | 读取报名和签到数据，生成名单和统计 |

## 4. 这样划分的原因

1. **按业务对象和生命周期拆分。** 报名记录、票券、签到记录的状态各自独立变化：报名有 6 种状态，票券只有有效和失效，签到一旦发生就不可撤销。拆成 M5、M6、M7 之后，每个模块只维护自己的状态，方便单独检查转换规则。
2. **名额相关的写操作集中在 M5。** 报名、退票、递补都会改变占用人数，放进同一模块、同一事务处理，才能保证最后一个名额不超卖（REQ-012），也保证候补顺序正确（REQ-010）。其他模块需要改变名额时（审核扩容、活动取消），都调用 M5 的接口，不直接改数据。
3. **申办和审核分开。** 组织者和管理员的操作对象相同，但权限和界面完全不同。拆成 M2 和 M3，与角色一一对应，便于权限检查。
4. **权限和日志做成横切服务。** 所有模块都需要鉴权（REQ-024）和记日志（REQ-019）。集中实现可以避免遗漏，也保证日志格式一致。
5. **消息单独成模块。** 现在只需要发候补入队提醒；以后若要扩展到其他事件或渠道，只改 M8，不影响报名逻辑。
6. **定时任务只调用业务接口。** 缺席和候补失效与用户请求走同一套状态转换规则，避免出现“后台改了状态、业务规则没检查”的情况。
